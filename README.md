# URL Shortener

A small web service that turns long links into short ones, redirects visitors to the original page, and counts clicks. It has a REST API, a SQLite database, a one-page web interface, an automated test suite, a Docker image, and CI.

## Why I built this

I wanted to build one small product from start to finish: define the problem, design an API, store data, build an interface, test it, package it, and automate the checks. A URL shortener is small enough to finish in a few days, but it has real design questions (redirect behavior, input validation, unique IDs, security) that I had to make decisions about and document.

## Product thinking

**Problem.** Long URLs are awkward to share in messages, slides, and print. People also want to know whether anyone actually used the link.

**Users.** Anyone who needs to share a link and see how often it is opened.

**User stories**

1. As a user, I paste a long URL and get a short link back.

2. As a visitor, I open the short link and land on the original page.

3. As a user, I see all my links with their click counts.

4. As a user, I delete a link I no longer want.

5. As a user, I get a clear error if I paste something that is not a valid web link.

**In scope:** create, redirect, count, list, delete, a basic web page.

**Non-goals (for now):** user accounts, custom aliases, link expiry, analytics beyond a total click count, rate limiting.

**Success criteria:** a short link always redirects to the right URL, clicks are counted correctly, invalid input is rejected, and the whole thing runs with a single Docker command.

## Features

* Shorten a URL into a random 6-character code

* Redirect from the short code to the original URL, with click counting

* List all links with click counts and creation time

* Delete links

* Input validation (only `http` and `https` URLs are accepted)

* Interactive API documentation at `/docs` (generated by FastAPI)

* Automated tests and a GitHub Actions CI pipeline

* Docker image for repeatable runs

## Architecture

```
flowchart LR
    B["Browser (index.html + fetch)"] -->|"JSON over HTTP"| A["FastAPI app (app/main.py)"]
    C["curl / other API clients"] -->|"JSON over HTTP"| A
    A -->|"parameterized SQL"| D[("SQLite via app/db.py")]

```

What happens when someone opens a short link:

```
sequenceDiagram
    participant U as Visitor
    participant A as FastAPI app
    participant D as SQLite
    U->>A: GET /aB3xYz
    A->>D: SELECT the row for this code
    D-->>A: original URL
    A->>D: UPDATE clicks = clicks + 1
    A-->>U: 307 redirect to the original URL

```

All SQL lives in `app/db.py`. The API layer in `app/main.py` never builds SQL itself, so the storage can change without touching the routes.

## API reference

Interactive docs are available at `/docs` while the server runs.

| **Method** | **Path** | **Description** | **Success** | **Errors** | 
| `POST` | `/api/links` | Create a short link | `201` with the new code | `400` invalid URL, `422` malformed body, `500` if no unique code could be generated | 
| `GET` | `/api/links` | List all links, newest first | `200` | none | 
| `DELETE` | `/api/links/{code}` | Delete a link | `204` | `404` unknown code | 
| `GET` | `/{code}` | Redirect to the original URL and count the click | `307` with a `Location` header | `404` unknown code | 
| `GET` | `/` | Web interface | `200` | none | 

**Create a link**

```
curl -X POST http://127.0.0.1:8000/api/links \
  -H 'Content-Type: application/json' \
  -d '{"url": "https://example.com/a/very/long/path"}'

```

```
{
  "code": "aB3xYz",
  "short_path": "/aB3xYz",
  "url": "https://example.com/a/very/long/path"
}

```

**Rejected input** (`400`)

```
{ "detail": "URL must start with http:// or https://" }

```

## Data model

```
CREATE TABLE IF NOT EXISTS links (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    code       TEXT UNIQUE NOT NULL,
    url        TEXT NOT NULL,
    clicks     INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

```

The `UNIQUE` constraint on `code` is what guarantees two links never share a short code. The database enforces it, not just the application.

## Design decisions and trade-offs

| **Decision** | **Why** | **Trade-off** | 
| Redirect with **307**, not 301 | Browsers cache a 301 permanently and would skip the server, so clicks would stop being counted. | Slightly more server traffic. | 
| Accept only `http` and `https` URLs | Prevents storing links like `javascript:...`, which would turn the redirect into an attack vector. | Rejects other schemes such as `ftp` on purpose. | 
| Codes generated with `secrets`, not `random` | Codes are unpredictable, so links cannot be guessed by counting up. | None that matters at this scale. | 
| 6 characters from 62 symbols (letters and digits) | 62^6 is about 56.8 billion possible codes, which is plenty for this project. | Collisions are possible in principle, so the code retries (up to 5 times) when the `UNIQUE` constraint rejects a duplicate. | 
| Raw SQL with `?` placeholders instead of an ORM | I wanted to understand exactly what queries run, and placeholders prevent SQL injection. | More boilerplate than an ORM. | 
| SQLite | Zero setup, one file, ships with Python. | Only one writer at a time, so it is not suitable for heavy concurrent traffic. | 
| Click count incremented in SQL (`clicks = clicks + 1`) | The increment happens atomically inside the database instead of read-modify-write in Python. | None. | 
| Front end sets `textContent`, not `innerHTML` | Prevents a stored URL from being interpreted as HTML (XSS). | Slightly more verbose DOM code. | 
| Database path read from the `DB_PATH` environment variable | Tests can use a temporary database, and Docker can mount a volume. | One more setting to document. | 

## Getting started

### Requirements

* Git

* Python 3.12 or newer

* Docker (optional, for the container workflow)

### Run locally

macOS / Linux:

```
git clone https://github.com/Youssef/url-shortener.git
cd url-shortener
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload

```

Windows (PowerShell):

```
git clone https://github.com/Youssef/url-shortener.git
cd url-shortener
py -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload

```

Then open <http://127.0.0.1:8000> for the web page or <http://127.0.0.1:8000/docs> for the API documentation.

### Terminal & Environment Notes

> **Windows Troubleshooting:** If you install a new command-line tool (like Docker Desktop) while VS Code is open, running terminals will not immediately recognize the command and will throw an `ObjectNotFound` error. Always kill your active terminal session and open a fresh one to reload your system's path variables.

### Run with Docker

```
docker build -t url-shortener .
docker run --rm -p 8000:8000 url-shortener

```

By default the database is lost when the container stops. To keep your data, mount a folder and point `DB_PATH` at it.

macOS / Linux:

```
docker run --rm -p 8000:8000 -v "$(pwd)/data:/data" -e DB_PATH=/data/links.db url-shortener

```

Windows (PowerShell):

```
docker run --rm -p 8000:8000 -v "${PWD}/data:/data" -e DB_PATH=/data/links.db url-shortener

```

### Configuration

| **Variable** | **Default** | **Purpose** | 
| `DB_PATH` | `links.db` | Location of the SQLite database file | 

## Testing and CI

```
pytest -v

```

The test suite covers:

* creating a link and following the redirect (checks the `307` status and the `Location` header)

* click counting across multiple visits

* rejecting invalid URLs, including a schemeless domain, `ftp://`, `javascript:`, and an empty string

* `404` for unknown codes

* deleting a link (`204`, then `404` on a second delete)

Every test runs against a fresh temporary database (pytest `tmp_path` plus an environment override), so tests never touch real data and never affect each other.

GitHub Actions runs the test suite on every push and pull request (see `.github/workflows/tests.yml`).

## Security notes and known limitations

This is a learning project, not a production service. Known gaps:

* **No authentication.** Anyone who can reach the server can create and delete links.

* **No rate limiting.** A client could create many links quickly.

* **No link safety checks.** The service does not scan destination pages for malware or phishing.

* **Single-node SQLite.** It does not scale across multiple servers.

* **No HTTPS in the container.** It would normally sit behind a reverse proxy that terminates TLS.

* **Dependencies are not pinned to exact versions yet** (see the roadmap).

Protections that are in place: parameterized SQL, URL scheme validation, unpredictable codes, safe DOM updates in the front end, and database-enforced uniqueness.

## What I learned

* How HTTP methods and status codes map to real behavior, and why 307 vs 301 changes whether clicks can be counted.

* How SQL injection works and how parameterized queries prevent it.

* How to isolate tests with fixtures and temporary databases so they are repeatable.

* How containers package an app and its dependencies, and why copying `requirements.txt` before the source code speeds up rebuilds.

* How container networking works in local development, specifically why a Docker container must be bound to `0.0.0.0` internally to accept outside connections, but must be accessed via `127.0.0.1` on the host machine browser.
